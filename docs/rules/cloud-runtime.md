# Cloud runtime (iOS)

Read before changing login, the data runtime, the offscreen WebView and watchdog, the host↔runtime contract, Streams grants or local persistence. These rules bind every caller of the area, not only files in its directory.

- Login is native, with each provider following [its native protocol](../native-auth.md#public-protocol) (GitHub/Discord through a one-use PKCE backend handoff). Never restore device-code polling or a Web login screen. `AuthSession` alone installs Keychain credentials, after account validation and cancellation checks after every suspension. Credential HTTP requests refuse all redirects and cookies; persist only the raw JSON `token`, never the signed `set-auth-token` cookie header, because Streams authorization looks up the raw session token. Never substitute desktop credentials for app authorization. Keep the sign-in page in step with web `/login` ([details](../native-auth.md#sign-in-page)).

- `data-runtime` in LodyKit owns the POC's catalog replicas, Streams reads, cursors and retry. Native sessions observe projected catalog events; do not add a second live replica. The old offline decoder is retained only as a comparison path.

- Swift owns the offscreen WebView and watchdog. Keep startup/heartbeat deadlines outside JS, ignore callbacks from replaced views, and bound automatic restarts. Background suspension is not a watchdog failure: retain the WebView and reset its heartbeat deadline on foreground; recreate only a missing or failed runtime. User-started sends use only a short UIApplication background allowance through reply synchronization; never request BGContinuedProcessingTask, which displays a system Live Activity, or use idle connection keepalive.

- The host↔runtime boundary is the versioned contract in `packages/cloud-runtime/src/contract`, with generated Swift in `packages/lody-core` (`pnpm contract`). Add methods there: the runtime exposes only `dataRuntime.receive` and posts only `ready` / `envelope`; do not add `callAsyncJavaScript` commands.

- Only short-lived workspace Streams grants enter the bundled WebView; long-lived Better Auth credentials stay in Keychain. Never load remote scripts or expose tokens in diagnostics. Logout and unsubscribe must stop the owned runtime.

- Explicit removal of a Loro pending message clears only its native Outbox record and does not require Roost accepted-input state. Preserve account/workspace and exact-input guards; local removal never claims to cancel remote execution. Roost removal continues through its pending-input owner.

- Explicit Loro handoff recovery first reads fresh server history for the exact input, then reuses the owner's deduplicated dispatch RPC with its persisted configuration. Never re-append the message, rewrite a newer dispatch pointer, revive a terminal/missing-history input, or infer execution from a delivery ACK. Readback failure keeps the Outbox record actionable; local removal and scope changes fence later recovery stages.

- This POC reads catalogs and session history, and sends text turns. CRDT replicas restore from server bootstrap. App account/workspace context and complete catalog display projections restore from SQLite in LodyKit before background authentication and sync; credentials remain in Keychain. Loro/Flock updates use uint32 big-endian length frames; never append raw WASM exports. Persist the user history before the durable dispatch pointer and Machine RPC. A machine ACK is delivery, not completion. Never automatically replay writes across runtime recovery. Catalog input is bounded to 16 MiB per bootstrap/catch-up window, including the bootstrap snapshot. Old-replica catch-up limits require a fresh bootstrap before a terminal limit. Publish a catalog only from healthy, synchronized metadata; pending or failed machine streams retain their last projection without blocking other machines. Their errors are diagnostics, not workspace `syncError`; machine operations still require that target to be ready.

- Session envelopes stay below the host's 12 MiB limit. Loro sessions keep the whole document in the runtime but send only a transcript window that starts at a user turn, follows new entries and grows by pages on `loadOlderSession`; usage, billing, execution and composer state still read the whole history. A window over the 8 MiB budget keeps its newest turns and stops offering older history. An envelope still over the limit becomes an overflow marker and records one `session_overflow` diagnostic with its size.

- Catalog and cached-settings recovery compare exact decimal byte offsets and the last snapshot size before preferring a newer snapshot. Failed size hints or oversized/incomplete optional replacements preserve incremental recovery. Frame import yields between 12 ms slices and checks scope cancellation. At most two machine replicas initialize concurrently; metadata and live reads bypass that queue. Catalog publication coalesces bursts over 16 ms and reads the current scope when it flushes.
- The trusted DataRuntime HTML permits `https:` and `wss:` connections; its other
  CSP directives remain restrictive. CSP permission alone does not enable the
  Streams WebSocket transport.
- The Status view layout and its writes come only from the shared Lody planner vendored verbatim in `packages/cloud-runtime/src/protocol/lody-shared` (hash-checked, golden vectors run in `apps/ios/tests/cloud/status-view.test.mjs`); refresh it from upstream, never edit or reimplement it, and never sort or classify those lists in Swift ([details](../../packages/cloud-runtime/README.md#status-view)).
- Bundled runtime code must run on the iOS 16.4 WebKit (the deployment target). Every esbuild bundle targets `safari16.4`. A Web API newer than 16.4 is either feature-guarded at its call or polyfilled by a module the runtime entry imports first, as `src/runtime/abort-signal-any.ts` does for `AbortSignal.any` (17.4); `apps/ios/tests/native/data-runtime.test.mjs` runs catalog sync with that API removed.
